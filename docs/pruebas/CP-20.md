# CP-20: Inicio de sesión por rol y acceso a una página de otro rol

| Campo | Valor |
| --- | --- |
| Caso | CP-20 |
| Tipo | Funcional / seguridad |
| Requisito(s) | RF-02 |
| Caso de uso | CU-01 |
| Pantalla | `index.html` y guardas de `auth.js` (`protegerPagina`) |
| Responsable | P3 |

## Precondiciones

- Cuentas de los 3 roles.

## Datos usados

| Dato | Valor |
| --- | --- |
| Variante probada | perfil con rol `profesional` abre `paciente/mis-citas.html` |
| Sin sesión | se abre `paciente/reservar.html?franja=100…` sin haber iniciado sesión |

## Pasos

1. Con rol profesional, abrir una página de `paciente/`.
2. Sin sesión, abrir una página privada.
3. Ejecución 2: con `paciente1`, abrir `admin/resumen.html`.

Código de consola:

No se usa la consola: todo se hace desde la interfaz.

## Resultado esperado

Cada rol llega a su inicio; el paciente ve "acceso denegado" y no se cargan datos.

### Pasos para la ejecución 2 (base real, la hace una persona)

1. En la URL publicada, iniciar sesión con cada cuenta demo y anotar a qué página llega (paciente → `paciente/index.html`, profesional → `profesional/agenda.html`, admin → `admin/resumen.html`).
2. Con `paciente1`, escribir en la barra la URL de `admin/resumen.html`: debe verse "Acceso denegado".
3. Desde la consola, intentar leer datos de admin (por ejemplo `supabase.rpc('citas_admin')`): debe responder `NO_AUTORIZADO`. Eso prueba que la base, no la página, niega el acceso.
4. Guardar capturas como `CP-20-real-N.png`.

## Observaciones

- **Qué prueba la ejecución 1.** Las páginas corren sin cambios, pero las respuestas de
  Supabase se reemplazan, con Chrome DevTools Protocol (`Fetch.requestPaused`), por
  respuestas con el formato exacto del contrato v1.1 (mismas columnas y mismos códigos de
  error en `message`). Así se prueba **la interfaz**: qué muestra, a dónde lleva y qué le
  pide a la base. **No** prueba la base: esa parte la cubren las pruebas de P2
  (`sql/pruebas_seguridad.sql`, 62/62 en Supabase) y la ejecución 2. El script de prueba
  usa Node y por eso **no** está en el repositorio (el proyecto no usa Node); el método
  está descrito en `docs/bitacora_ia.md`.
- Los agentes no tienen las contraseñas de las cuentas demo (las tiene el coordinador,
  fuera del repo), por eso la ejecución 2 la hace una persona.
- **Falta** el caso del plan (paciente abre `admin/resumen.html`) porque las páginas de admin son de P4 y aún no están en `main`.
