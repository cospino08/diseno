# CP-21: Reserva con perfil incompleto

| Campo | Valor |
| --- | --- |
| Caso | CP-21 |
| Tipo | Regla de negocio |
| Requisito(s) | RF-05 |
| Caso de uso | CU-02, CU-04 |
| Pantalla | P-05 `paciente/perfil.html`, P-03 `paciente/reservar.html` |
| Responsable | P3 |

## Precondiciones

- Usuario nuevo (rol paciente) sin documento, teléfono ni fecha de nacimiento.

## Datos usados

| Dato | Valor |
| --- | --- |
| Perfil simulado | `nombres = 'Nuevo Prueba'`, demás campos `null` |
| Datos para completar | `TEST-0099`, `300 123 4567`, `1995-02-03` |

## Pasos

1. Con el perfil incompleto, abrir **Buscar**.
2. Pulsar **Guardar cambios** con los campos vacíos.
3. Completar los datos y guardar.

Código de consola:

```js
// Ejecución 2, saltando la interfaz (cuenta nuevo1@demo.test, perfil incompleto):
const { data, error } = await supabase.rpc('reservar_cita', { p_schedule_id: <id de franja libre> });
console.log(error?.message);   // esperado: 'PERFIL_INCOMPLETO'
```

## Resultado esperado

`PERFIL_INCOMPLETO`; la interfaz abre el perfil.

## Observaciones

- **Qué prueba la ejecución 1.** Las páginas corren sin cambios, pero las respuestas de
  Supabase se reemplazan, con Chrome DevTools Protocol (`Fetch.requestPaused`), por
  respuestas con el formato exacto del contrato v1.1 (mismas columnas y mismos códigos de
  error en `message`). Así se prueba **la interfaz**: qué muestra, a dónde lleva y qué le
  pide a la base. **No** prueba la base: esa parte la cubren las pruebas de P2
  (`sql/pruebas_seguridad.sql`, 62/62 en Supabase) y la ejecución 2. El script de prueba
  usa Node y por eso **no** está en el repositorio (el proyecto no usa Node); el método
  está descrito en `docs/bitacora_ia.md`.
- Los agentes no tienen las contraseñas de las cuentas demo (las tiene el coordinador,
  fuera del repo), por eso la ejecución 2 la hace una persona.
- El documento repetido también se probó: con el error `23505` en `uq_profiles_documento`, aparece "Ese número de documento ya está registrado en otra cuenta." bajo el campo.
